# القياسات (v0.1) — أرقام حقيقية، مع الأمر الذي أنتجها

**قاعدة:** لا رقم هنا بلا أمر يعيد إنتاجه. الأرقام تختلف من جهاز لآخر؛ قارن دائماً على نفس الجهاز
وفي نفس الجلسة. «الجهاز الآلي» = جهاز Linux مشترك (ضوضاء من عمليات أخرى ممكنة)؛ «مشغّل GitHub» =
جهاز Windows Server افتراضي مشترك، **ليس جهاز مستخدم**.

## 1) المحرّك: تعدد الاتصالات مع خادم يحدّ كل اتصال

الحالة التي يفيد فيها مدير التحميل فعلاً: خادم يعطي كل اتصال سرعة محدودة (هنا 4 م.ب/ث لكل اتصال).
المقارنة بين **v0.0.1** (المنشور، مبني من الوسم) و**v0.1** على نفس الجهاز، كل ملف متحقق منه بـSHA-256.

```
cargo build --release -p eid-cli -p eid-testserver
python3 scripts/bench/engine_bench.py --suite throttled --size 268435456 --throttle 4194304 --conns 16,32
python3 scripts/bench/engine_bench.py --suite throttled --size 67108864  --throttle 4194304 --conns 8
# v0.0.1: git worktree add /tmp/eid-base v0.0.1 && (cd /tmp/eid-base && cargo build --release -p eid-cli)
#         ثم نفس الأوامر مع --eid /tmp/eid-base/target/release/eid
```

| الحجم | الاتصالات | v0.0.1 | v0.1 | التحسن |
|---|---|---|---|---|
| 64 MiB | 8 | 3.08 ث | 2.47 ث | ‎−20%‎ |
| 256 MiB | 16 | 6.63 ث | 4.91 ث | ‎−26%‎ |
| 256 MiB | 32 | 6.63 ث (38.6 MiB/s) | 3.35 ث (76.4 MiB/s) | **ضعف السرعة** |

السبب: v0.0.1 كان يزيد الاتصالات واحداً كل نبضة؛ v0.1 يبدأ بواحد ويضاعف (1، 2، 4، 8) ما دامت
السرعة ترتفع 10% على الأقل، ثم واحداً واحداً (`Ramp` في `crates/eid-engine/src/download.rs`،
مع اختبارات `ramp_tests`). v0.0.1 لم يصل فعلياً إلى 32 اتصالاً قبل نهاية ملف 256 MiB.

بلا تحديد سرعة (loopback): نحو 430 MiB/s للإصدارين — الحد هنا القرص/الذاكرة لا المحرّك، فلا فرق
يُدّعى. الذاكرة القصوى لعملية `eid`: نحو 20–25 MiB في الحالتين (جهاز مشترك، القياس متذبذب).

**على Windows:** خطوة «Engine speed on Windows» في `ci-windows.yml` تشغّل
`scripts\windows\compare_idm.ps1 -SkipIdm` (64 MiB، 4 MiB/s لكل اتصال، 1/8/16 اتصالاً، 3 مرات)
وترفع `engine-windows/results.json` كـartifact. الأرقام في قسم «أرقام CI» أدناه.

**مقارنة مع IDM:** لم تُجرَ — IDM غير موجود على أجهزة CI ولا يجوز تثبيت برنامج مدفوع عليها.
السكربت جاهز للتشغيل على جهازك: `docs/OWNER-ACTIONS.md` §3.

## 6) v0.2: هل تفيد إعادة استخدام الاتصال؟ (قياس قبل أي تغيير، ADR-0012)

السؤال: المحرّك يفتح اتصال TCP جديداً لكل طلب (`pool_max_idle_per_host(0)`، لضمان سقف الاتصالات).
كم اتصالاً يفتح التحميل فعلاً، وكم تكلّف المصافحة؟ أُضيف للخادم التجريبي `--connect-delay-ms`
(كل اتصال **جديد** ينتظر قبل أول طلب، كأنها جولات مصافحة TCP+TLS يتخطاها الاتصال المعاد استخدامه)
وعدّاد للاتصالات والطلبات لكل تحميل (`STATS`). الجهاز: Linux، 4 أنوية، loopback، 2026-11-19.

```
cargo build --release -p eid-cli -p eid-testserver
python3 scripts/bench/engine_bench.py --suite throttled --size 268435456 --throttle 4194304 --conns 16,32 --reps 3 --connect-delay-ms 0|50|150
```

| تأخير الاتصال الجديد | الاتصالات | الزمن (وسيط 3) | MiB/s | اتصالات TCP | طلبات HTTP | ذروة RSS | CPU |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 0 | 16 | 4.88 ث | 52.5 | 16 | 16 | 18.3 MiB | 0.75 ث |
| 0 | 32 | 3.39 ث | 75.6 | 32 | 32 | 18.3 MiB | 0.70 ث |
| 50 م.ث | 16 | 5.03 ث | 50.9 | 16 | 16 | 18.4 MiB | 0.75 ث |
| 50 م.ث | 32 | 3.48 ث | 73.6 | 32 | 32 | 18.4 MiB | 0.71 ث |
| 150 م.ث | 16 | 5.24 ث | 48.8 | 16 | 16 | 18.3 MiB | 0.70 ث |
| 150 م.ث | 32 | 3.71 ث | 68.9 | 32 | 32 | 18.3 MiB | 0.75 ث |

كل ملف متحقق بـSHA-256. **النتيجة:** في تحميل ملف كبير واحد، عدد الاتصالات = عدد الطلبات = عدد
الاتصالات المطلوب؛ المحرّك لا يفتح اتصالاً زائداً، فإعادة الاستخدام **لا توفّر شيئاً هنا**. كلفة مصافحة
150 م.ث كلها نحو 0.3 ث (≈10%) لأن الاتصالات الـ32 يجب أن تُفتح على أي حال.
**ما لم يُقس:** خوادم تقطع الاتصال كثيراً (كل إعادة محاولة بعد القطع تحتاج اتصالاً جديداً في كل الأحوال)،
وقائمة طويلة من ملفات صغيرة من نفس الخادم (هنا قد تفيد إعادة الاستخدام؛ لا توجد أداة قياس لها بعد).
**القرار المقترح:** يبقى ADR-0012 مؤجلاً؛ لا تغيير في الاتصالات بلا قياس يثبت فائدة.
