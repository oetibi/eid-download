# P1 independent review

Review date: 2026-11-13. Verdict: do not close P1.

Scope: AGENTS, README, REQUIREMENTS, ARCHITECTURE, PLAN G1–G4, ADRs (including 0009), engine implementation/tests, platform filesystem/process implementation, CLI/tests, testserver, required-test checker/list and CI workflows. Findings below are static code findings unless explicitly marked reproduced. No source, test or Cargo files were edited.

Validation: `cargo clippy --offline --workspace --all-targets -- -D warnings` exited 0. `cargo test --offline --workspace --no-fail-fast` exited 101 (seven failed targets); loopback listener creation was denied by this sandbox (`Operation not permitted`). These failures are not evidence of engine regressions or passing network gates. Platform unit tests: 8 passed; architecture guards: 4 passed. Windows behavior and release tests were not run. A separate offline experiment under `/tmp` reproduced B2 using the existing `target/debug/eid` binary.

## Blocker

### B1 — Restart can destroy data still certified by an old checkpoint

**Location:** `crates/eid-engine/src/download.rs:1134`, `:1173`, `:1202`; `crates/eid-engine/src/state.rs:159` (backup rotation).

**Why:** After ServerChanged, the next iteration truncates the same part file before replacing the old durable state. The old checkpoint and backup still certify completed bytes belonging to the previous representation. The initial state write also rotates the old checkpoint into `.bak`. Checksum validation authenticates neither the data generation nor its contents.

**Failing scenario:** A partially checkpointed representation A changes to same-length B. Restart truncates/preallocates the part, then the process dies before the new initial state is installed. Resume loads A's nonzero frontiers. If the origin serves A again with its old validator, only the tails are fetched, leaving holes or B bytes in checkpointed regions. Default engine configuration has no expected digest and can publish corrupt data. Backup recovery can similarly pair an old generation with new-generation data.

**Suggested fix:** Give each restart a separate data generation and atomically switch a manifest referencing it; never modify data certified by recoverable state. Alternatively durably invalidate both primary and backup before destructive truncation, with an explicit recoverable restart state. Add crash tests between truncation, preallocation, initial-state rotation and replacement, including A→B→A.

### B2 — Missing part plus any same-size final file is treated as completion

**Location:** `crates/eid-engine/src/download.rs:1305–1333`.

**Why:** The recovery shortcut does not require completed segment coverage or a recorded finalization transaction. It accepts an unrelated final file solely by length. Computing its SHA does not compare it with an authoritative expected hash.

**Failing scenario (reproduced):** Create a valid sealed state with total 4, frontier 1, URL `http://127.0.0.1:1/unreachable`, no part, and `f.bin` containing `EVIL`. `eid resume ... -q` exits 0, prints `f.bin` and deletes the state without contacting the origin. This used only `/tmp` files. It also misidentifies completion after the actual final rename chose a numbered name because the base name appeared during transfer.

**Suggested fix:** Persist a finalization record with completed coverage, exact chosen destination and content identity before renaming. Recover only that transaction and verify the recorded digest; otherwise restart or report missing data. Test unrelated same-size files and numbered-destination crashes.

### B3 — Segmented transfers without validators can splice different representations

**Location:** `crates/eid-engine/src/download.rs:1143–1177`, `:168–181`, `:255–278`.

**Why:** `can_resume` is discarded. A validator-free 206 still enables multiple workers and reconnects; same total length is the only representation check. Refusing cross-session resume without validators does not protect an ongoing segmented session.

**Failing scenario:** A server provides ranges but no ETag/Last-Modified, changes a same-sized file after the probe, and answers later ranges from the new file. Segment zero contains A and tails contain B. Coverage is complete and the engine publishes the splice. Existing change tests supply ETag or Last-Modified.

**Suggested fix:** Without a trustworthy validator, consume only the original response as one stream. After a disconnect restart the whole representation. Add same-size changes without validators during splits and retries and compare final SHA with coherent versions.

### B4 — Windows hard links permit writes to external victim files

**Location:** `crates/eid-platform/src/fs.rs:74–84`; `crates/eid-engine/src/download.rs:1347–1384`; `crates/eid-engine/tests/security.rs:137`.

**Why:** Windows handle validation omits the hard-link count entirely. The engine opens the part read/write and preallocates it. The protective resume tests are compiled only on Unix. This violates the permanent P1 safety requirement on the product's primary OS; it is not merely missing manual evidence.

**Failing scenario:** Replace a cancelled part with an NTFS hard link to another writable same-user file of a plausible length. Resume accepts it, resizes it and writes ranges into the external victim.

**Suggested fix:** Inspect link count and file identity using the opened Windows handle and reject multiple links before mutation. Run the victim-preservation test on Windows, failing loudly if link creation fails.

## Major

### M1 — No exclusive job ownership; concurrent resumes corrupt persistence and data

**Location:** `crates/eid-engine/src/download.rs:1292–1347`; `crates/eid-engine/src/state.rs:141–165`.

**Why:** `create_new` only arbitrates initial downloads. Resume opens an existing part without an exclusive job lock; every writer shares the same `.tmp`, primary and backup names. There is no lock covering state loading through finalization.

**Failing scenario:** Start two `eid resume` processes for one sidecar. Both write and checkpoint; either removes the other's temp, rotates its state, or renames the part while the other is active. If one detects a change, it deletes/restarts the other's data. A cancelled old-generation writer can persist state over a new generation.

**Suggested fix:** Acquire a platform-backed exclusive per-job lock before loading state and retain it through finalization/restart. Use unique temp files as a second defense. Test simultaneous CLI resumes and resume versus an active original job.

### M2 — Finalization trusts a pathname after dropping the verified file handles

**Location:** `crates/eid-engine/src/download.rs:1241–1269`; `crates/eid-platform/src/fs.rs:257` (`rename_noreplace`).

**Why:** The verified data handle is closed before hashing and promotion; hashing reopens a path, closes it, and promotion resolves the path again. A same-directory actor can replace the part between these operations. Unix promotion hard-links whatever inode the pathname currently names, then separately unlinks the source. No identity check connects the promoted file to the downloaded handle.

**Failing scenario:** In a shared writable destination, rename the actual part aside and substitute another regular file after hashing but before promotion. The reported SHA is for the downloaded file, while the published destination contains the substitute. A symlink substitution can also be promoted on Unix. The tests plant links only before claiming, not during finalization.

**Suggested fix:** Protect the directory/job against substitution, retain and compare file identities, and implement platform promotion tied to the verified object with a documented race-safe protocol. Add deterministic substitution hooks around hash/promotion and verify the final destination itself.

### M3 — HTTP response headers have no read deadline

**Location:** `crates/eid-engine/src/http.rs:35–43`; `crates/eid-engine/src/download.rs:594–597`, `:349–352`.

**Why:** `connect_timeout` ends after connection establishment. `stall_timeout` wraps only body reads, after `.send()` returns headers. A server that accepts TCP and never finishes headers blocks forever unless the user cancels.

**Failing scenario:** A local fixture accepts the socket and sends a partial header once, then stops. Neither probe attempts nor ranged retries reach their stall timeout or retry budget. The current slow-loris test stalls only the body.

**Suggested fix:** Apply a cancellable response-header deadline to every send (and account for redirects), or configure an appropriate read timeout. Test no headers and trickled incomplete headers, paired with successful slow responses.

### M4 — Dropping the public download future leaves uncancellable disk work running

**Location:** `crates/eid-engine/src/download.rs:309–323`, `:841–848`, `:876`, `:1007–1010`.

**Why:** Cooperative cancellation drains workers, but dropping/aborting the outer future drops its JoinSet and aborts async workers while `spawn_blocking` writes/checkpoints continue. No lifetime guard retains job ownership until those operations finish. The cancellation test exercises only token cancellation.

**Failing scenario:** An app aborts a download task during a checkpoint and immediately resumes its sidecar. The old blocking closure can later replace the new state; an old write can overlap resumed writes. Aborting during initial persistence can also leave a claimed part without a usable sidecar after an error.

**Suggested fix:** Supervise the job independently of the caller future, retaining exclusive ownership until all disk operations drain. Dropping the handle should request cancellation, not drop supervision. Test task abort/drop at write, checkpoint and initial-save barriers, then immediate resume.

### M5 — File privacy requirements are bypassed and their tests are vacuous

**Location:** `crates/eid-engine/src/download.rs:746`; `crates/eid-platform/src/fs.rs:109–125`; `crates/eid-engine/tests/security.rs:294`; `crates/eid-engine/src/state.rs:292`.

**Why:** Part files use normal umask-derived permissions, commonly 0644. Windows `private` is ignored and state inherits arbitrary destination ACLs. Privacy assertions accept `None` as success, and the generated-part-and-state test inspects only the state.

**Failing scenario:** Download sensitive authenticated content into a traversable Unix directory with umask 022: another user can read the part. On Windows a shared destination grants other users access to state (including signed URL queries) despite a green privacy test.

**Suggested fix:** Create parts and sidecars owner-only, using a protected Windows DACL. Assert actual access restrictions on both files and backups, including a permissive parent directory. Do not count unknown ACL results as proof.

### M6 — Windows required-test gate is impossible, while other Windows tests silently succeed

**Location:** `.github/workflows/ci-windows.yml:33`; `scripts/required_tests.txt:49–51`, `:68–72`; `crates/eid-engine/tests/security.rs:137`, `:280–290`; `crates/eid-engine/tests/g4_tls.rs:5`; `crates/eid-cli/tests/cli.rs:348–351`.

**Why:** Windows invokes the universal required-test checker, but that list requires Unix-only link tests and all Linux-only TLS tests. They cannot appear in Windows output, so the checker must fail. Conversely the Windows Ctrl-C test starts a child, waits, performs no assertions, and drops the child without waiting/killing it. The symlink precheck only asserts capability on Unix.

**Failing scenario:** A clean Windows CI run reports required names NOT RUN even if every available test passes. The Ctrl-C test reports `ok` without sending Ctrl-C or validating recovery and can leave its child alive. A failed Windows symlink capability probe also reports `ok`.

**Suggested fix:** Declare explicit OS-specific gates and documented exclusions; implement actual Windows equivalents for required security behavior. Make capability failures fail. Exercise Windows console cancellation and reap children on every test exit.

### M7 — Gate evidence is weaker than PLAN and ADR-0009 require

**Location:** `crates/eid-engine/src/table.rs:239` (`handoff_randomized_200_seeds`); `crates/eid-engine/tests/g3_segments.rs:14`, `:165`, `:306`; `crates/eid-engine/src/fault.rs:31–41`; `crates/eid-cli/tests/cli.rs:155`.

**Why:** The 200-seed arbiter tracks write counts, but never writes content or computes SHA; its simulated disconnect occurs after completing the whole reservation. The whole-engine jitter test has only 30 seeds and the seed is merely an on/off switch: jitter uses unseeded thread-local `fastrand`, so the interleaving is not reproducible from the printed seed. The connection matrix is 20 MiB rather than the planned 50 MB; 32 configured connections only asserts peak >1. The 429 test uses wall time rather than the required paused clock. The CLI kill threshold is 2 MiB out of 12 MiB, below the required 30%.

**Failing scenario:** A data-offset bug can pass the 200-seed counter model; a jitter race cannot be replayed by seed; a regression limiting 32 requested connections to two can pass the matrix. None of these named green results proves the stronger advertised gate.

**Suggested fix:** Fulfil the existing gates without changing PLAN: run at least 200 whole-engine seeded fault schedules, verify SHA and write bounds, inject failures during reservations/writes, record replayable schedules, use the specified transfer size, assert meaningful concurrency, use virtual time for retry timing, and wait for ≥30% durable progress before kill.

## Minor

### m1 — Long-name collision numbering can erase its own suffix

**Location:** `crates/eid-engine/src/download.rs:714–719`; `crates/eid-engine/src/sanitize.rs:35–45`.

**Why:** Numbering appends ` (n)` and then truncates the stem back to 200 bytes. With an already maximal stem, truncation removes the number itself. All 999 candidates may equal the occupied base.

**Failing scenario:** Download a URL twice with a 200-byte ASCII name and no extension (or a maximal stem with a short extension). The first succeeds; the second repeatedly checks the same name and fails to find a free filename despite available names.

**Suggested fix:** Reserve bytes for the collision suffix before truncating the original stem. Test maximum ASCII and Arabic names with actual existing-file collisions, not only suffix length limits.

### m2 — Blocking filesystem and hashing operations execute inside async jobs

**Location:** `crates/eid-engine/src/download.rs:1074–1085`, `:1134–1136`, `:1200`, `:1234–1269`, `:1292`, `:1384`.

**Why:** Synchronous metadata, state loading, preallocation, sync, full-file hashing and finalization run directly on Tokio executor threads. This violates AGENTS §6.7; moving only individual writes/checkpoints to `spawn_blocking` does not cover these paths. Download and resume also duplicate context initialization/restart/finalization setup, making lifecycle fixes easy to apply inconsistently.

**Failing scenario:** Hash a large completed file or preallocate on a slow/non-sparse filesystem in a single-thread runtime: unrelated jobs, timers and cancellation stop being polled for the duration.

**Suggested fix:** Move complete blocking lifecycle operations to the blocking pool under the same job-ownership supervisor. Share download/resume lifecycle construction and test executor responsiveness during deliberately blocked filesystem operations.

### m3 — HTTP-date Retry-After is deliberately ignored

**Location:** `crates/eid-engine/src/http.rs:115–119`.

**Why:** Only integer delta seconds are honored. A legitimate HTTP-date Retry-After falls back to a short exponential delay, sending requests before the server's stated deadline.

**Failing scenario:** A 429 specifies a date two minutes in the future. Workers retry after milliseconds/seconds and repeatedly trigger throttling instead of waiting.

**Suggested fix:** Parse the HTTP-date form with bounded arithmetic and the configured cap; test future, past, malformed and extreme dates with an injected clock.
