## Major

### M1 — Pipe squatting: the Windows client never verifies who owns the server

**Location:** `crates/eid-platform/src/ipc.rs:364–381` (`connect`), `crates/eid-ipc/src/client.rs` (`Client::connect`).

**Why:** The pipe name `\\.\pipe\EidDownload-<SID>-main` is predictable, the pipe namespace is global, and `ClientOptions::new().open()` does no check of the server process or its SID. *(Erratum, 2026-11-15: this sentence originally also claimed the default QoS lets the server impersonate the client. That was wrong: tokio's `ClientOptions` defaults to `SECURITY_IDENTIFICATION`, which prevents impersonation.)* The client then sends the token and later the URLs. The server's DACL protects only the pipe the app created itself.

**Failing scenario:** User B creates `\\.\pipe\EidDownload-<A's SID>-main` before A's app starts (a SID is enumerable). A's `eid add URL` or the native host connects to B's pipe and sends A's token (read from A's token file) and A's URL, possibly with a signed query. Because `first_pipe_instance(true)` then fails for A's real app (`AddrInUse` → "already running"), `eid serve` takes the "second instance" path and forwards to B. On Unix the private `0700` directory prevents this; ADR-0002 does not discuss it.

**Suggested fix:** Before sending anything check the server's process owner (`GetNamedPipeServerProcessId` → token SID == current user). Add a test that squats the name with a pipe owned by another principal (or a different DACL/SID) and asserts the client refuses it. Document in ADR-0002. If the owner prefers to defer, record it in DESIGN_NOTES and keep the "not tested / designed to be isolated" wording.

### M2 — The Windows security tests are not in the required gate

**Location:** `scripts/required_tests.txt:201–202`, `scripts/check_required.py`.

**Why:** `windows_pipe_has_a_protected_dacl_with_only_the_current_user`, `the_dacl_checker_rejects_everyone_and_other_principals_and_sddl_text_uses_aliases` and `windows_registers_under_hkcu_reads_back_and_unregisters` are the only tests of the P3 pipe DACL and HKCU registration, but the checker has no `windows:` prefix, so they are only comments. PLAN rule 4 says phase gates are (a) = names verified by `check_required.py`. Deleting or `#[ignore]`-ing them would keep CI green.

**Suggested fix:** Add a `windows:` (and `linux:`) prefix to `check_required.py` and list those tests. This changes the gate script, so it needs the owner's approval (AGENTS §9).

### M3 — A test named for symlink refusal does not test symlinks

**Location:** `crates/eid-ipc/tests/ipc.rs:442` (`a_symlinked_or_garbage_token_file_is_refused_by_the_client`), listed in `required_tests.txt`.

**Why:** The body only writes garbage and deletes the file. No symlink or hard link is ever created. `read_token_file` does use `open_regular_nofollow_read`, but the claim in the test name/required list is unproven. AGENTS §6.1 asks for symlink tests that fail if the link cannot be created.

**Suggested fix:** Add the symlink case (fail loudly if the link cannot be created; Unix and Windows with the CI privilege) or rename the test to what it does.

### M4 — A privacy assertion silently disappears on Windows, and token-file privacy there is unverified

**Location:** `crates/eid-platform/src/ipc.rs:544` (`if let Some(only) = owner_only(..)`), `crates/eid-platform/src/fs.rs:708` (`owner_only` returns `None` on Windows), `ipc.rs:427` (doc: "inherits the ACL of its directory").

**Why:** On the platform where the token matters most, `token_file_roundtrip_is_private_*` never checks privacy, and the file is created with the inherited ACL (`create_new_private` sets no DACL on Windows). AGENTS §5 says no test may skip silently; AGENTS §3 item 3 says files are created `create_private`. DESIGN_NOTES lists "DACL for data files" as not done but does not say the token file is in that set. MANUAL-TESTS #15 still says the protected DACL is "a P3 task" although it was not done.

**Suggested fix:** Either implement a protected DACL for the token file (same helper as the pipe) and assert it structurally, or make the test report "not verified on Windows" explicitly and add the token file to MANUAL-TESTS #15; correct the #15 wording.

### M5 — A vacuous secrecy assertion, and an undocumented decision about query tokens

**Location:** `crates/eid-cli/tests/serve.rs:361`.

**Why:** `!file.contains("QUERYSECRET") || file.contains("token=")` is always true when the secret is present with its key. The queue file does store the query string (`parse_and_strip` removes userinfo and fragment only), while `urlsafe::redact` states that "query strings often carry signed tokens" and logs/lists redact them. So the test claims a protection it does not check, and whether `queues.json` may hold signed query tokens is nowhere decided. The user:password part is correctly removed and checked in the written file.

**Suggested fix:** Assert the actual intended behaviour (secret present or absent), and record the decision in DESIGN_NOTES. AGENTS §6.3 should be read explicitly for query tokens.

## Minor

- **m1 — The real launch path is untested end to end.** `nm_binary_launches_the_app_as_a_detached_process_*` and `nm_starts_the_app_once_*` use `examples/fake_app.rs`/a fake launcher. Nothing runs the host starting the real `eid serve --endpoint .. --token-file ..` with null stdio and detached. Also ARCHITECTURE.md:24 says the host starts the app with `--background` and "stdio set binary on Windows"; the code uses `serve …` and does nothing special (Rust does not need it). Align the document or add the test.
- **m2 — Test name overclaims.** `crates/eid-native-host/tests/relay.rs:328` (`nm_survives_the_app_restarting_between_messages_without_double_running`) uses two different ids, so it cannot show "no double run" across a restart; the limit (retried id after restart runs again) is documented in STATUS/DESIGN_NOTES, so the name should not imply otherwise.
- **m3 — Server writes have no timeout.** `crates/eid-ipc/src/server.rs:104` (`send`) and the handshake reply can block forever if the peer never reads (up to 1 MiB reply), holding one of the 64 connection slots; `idle_timeout` covers reads only. Same-user peers only.
- **m4 — Token written after the endpoint is bound.** `crates/eid-ipc/src/lib.rs:60` (`start`): a client connecting in the gap reads the previous run's token and gets an auth error. The host retries until its deadline, but `call_retrying` (`crates/eid-cli/src/remote.rs:130`) tries twice back to back with no pause, and `eid serve` treats an auth failure as "already running".
- **m5 — Gap between pipe instances.** `crates/eid-platform/src/ipc.rs:354–361` (`accept`): between a client connecting and the next instance being created there is no instance, so a client arriving then gets `NotFound` ("app not running"). The cost is a pointless second launch attempt that fails to bind. If `create_instance` fails there, the connected instance stays in `next`, which can make `accept` return the same connection twice.
- **m6 — Possible double listener on Unix.** `ipc.rs:160`: two starters that both find the same stale socket can both `remove_file` and the second then removes the first's fresh socket. Unix path never ran here (builds only).
- **m7 — Panic under the scheduler lock.** `handle_once` uses `catch_unwind`, but a panic inside `Scheduler::edit` (P2 code) holds `inner.qs.lock().unwrap()` and would poison it, after which every request is "internal error" and the scheduler loop panics.
- **m8 — Small hardening/doc nits.** `config_dir()` (`ipc.rs:471`) does not require `%APPDATA%` to be absolute (unlike `dirs.rs`); `eid list` prints server-supplied `last_error` text with control characters unfiltered (`serve.rs:162`, `remote.rs`); the polling `loop { sleep(100ms) }` in `serve.rs` tests waits for the queue file instead of an event (AGENTS §7).
- **m9 — Pre-existing flaky test.** `throttle_and_first_slow_connections` failed once in a full run and passed 3/3 alone (see Validation). Not P3, not required, but it can make a CI run red.
- **m10 — Dedup is global by id.** The cache is keyed by the client-chosen id across all connections and stores error replies too (a transient failure replays for the same id). The P6 extension must generate a unique id per user action; note this in the P6 brief.
