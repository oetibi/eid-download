## Major

### M1 — Ctrl-C is ignored outside the download step
**Where:** `crates/eid-cli/src/main.rs:150-158`, `crates/eid-cli/src/video.rs:300-307` and `:589`, `crates/eid-media/src/tools.rs:192-199`.

**What happens:**
- `video_main` installs a `tokio::signal::ctrl_c` handler that only cancels a token.
- Only the download in `get`, the playlist listing and the playlist item downloads watch that token.
- During the tool install (~230 MB from GitHub), the `-J` step of `get` and the interactive consent prompt, Ctrl-C prints "stopping the tool…" and nothing stops.
- The handler stays registered (Windows console control handler, Unix signal-hook), so later Ctrl-C presses are swallowed too. Only closing the terminal or killing the process ends `eid`.
- If the install is interrupted by a kill, the `.staging-<random>` folder (with `.eid-part` files of the engine) stays in the tools root. Its cleanup (`install`, line 196) only runs when `install_into` returns, not when the future is dropped.

This conflicts with AGENTS §6.6 (cancellation at every `await`) and the help text ("Ctrl-C stops the tool and everything it started").

**Fix:**
- Put `ensure_tools`, `runner.info` (in `get`) and the consent prompt in `tokio::select!` against `cancel`, exiting with 130.
- Clean up the install staging folder with a drop guard, or remove stale `.staging-*` folders at the next install.
- Tests: cancel during the tool install (stalled `eid-testserver` asset) and during `-J` (fake stall mode). Assert exit 130, that the process ends within a bound, and that no `.staging-*` folder is left.

### M2 — A substring match on stderr can make a playlist item "unavailable" for good
**Where:** `crates/eid-media/src/hints.rs:313-368`, `crates/eid-cli/src/video.rs:820-834`.

**What happens:**
- `classify` lowercases the whole redacted stderr tail (up to 64 KiB, WARNING lines included) and looks for substrings such as "video unavailable", "does not exist", "javascript runtime", "--username".
- In a playlist, `Unavailable`, `SignInRequired`, `Drm` and `Geo` set `Status::Unavailable`. That is never retried (`video.rs:745`), counts as "gone", and the run exits 0. No command resets it.
- From public yt-dlp issue reports (not checked online in this review), YouTube answers "Video unavailable. This content isn't available" while it is rate-limiting a client. During one such episode, every remaining item of a large playlist could be marked unavailable permanently, against F11a(4)/(5).
- `tool_errors_get_hints` only tests single, clean messages; nothing tests a warning together with a different error.

**Fix:**
- Classify only lines that start with `ERROR:` (the last one first).
- Treat only `Drm` and the listing's `availability` (`private`, `needs_auth`…) as permanent. Keep tool-reported "unavailable" as retryable, either with a counter or a timestamp in the state, or with an explicit `--retry-unavailable`. This choice needs the owner.
- Test with a mixed stderr (a WARNING matching one hint plus an ERROR of another kind), and with a "Video unavailable" error followed by a later run that succeeds.

### M3 — Losing `.eid-playlist.json` breaks the numbering rules
**Where:** `crates/eid-media/src/playlist.rs:143-167`, `crates/eid-cli/src/video.rs:712-713`.

**What happens:**
- With no state file, `plan(None, …)` numbers items by their current position and recomputes the width, even when the folder already holds `NN - …` files and a non-empty `.eid-archive.txt`.
- An item added at the top after the loss gets `01` next to the existing `01 - Alpha.mp4`. A playlist that grew past 99 switches to width 3 next to width-2 files.
- This breaks D8 rules 1, 2 and 6 and F11a(3) ("never reused").
- `playlist_sync_downloads_only_new_items_via_the_archive` (`playlist.rs:516-524`) only checks that nothing is downloaded twice after the loss, not the numbers.

**Fix (needs an owner decision):**
- Either refuse with a clear message when there is no state but the archive is non-empty or `<digits> - ` files exist,
- or rebuild the state from the existing names (number prefix, width from the prefix length) and refuse if that is ambiguous.
- Test: delete the state, prepend an item, run again, and assert that no number appears twice and the old names are kept.

### M4 — `--quality best` / `<height>p` can fail after a complete download
**Where:** `crates/eid-media/src/args.rs:361-375`, `crates/eid-cli/src/video.rs:596-600, 638, 733-737, 786`.

**What happens:**
- The format strings fall back to `/b` (one file with video and audio). In that case yt-dlp does not merge, so `--merge-output-format mp4` has no effect and the file keeps its own container (webm, flv, 3gp…).
- `finished_file(&staging, "mp4")` then fails with "left no .mp4 file" and the staging folder is kept.
- On every rerun yt-dlp reports the file as already downloaded and exits 0, so the same error repeats forever. In a playlist the item fails on every run, and the run exits 1 every time.
- The fake tool always writes mp4, so this path is untested; with the real yt-dlp it is "not tested".

**Fix:**
- Add `--remux-video=mp4` to `ALLOWED`, emit it for the video qualities and record it in ADR-0003. Or accept and publish the extension the tool really produced (from a fixed list).
- Add a fake mode that writes `<id>.webm` and test both `get` and `playlist`.

### M5 — Unix: the process-group kill runs after the child is reaped, and twice
**Where:** `crates/eid-platform/src/process/supervised.rs:238-256` and `:509-513`.

**What happens:**
- `wait()` reaps the direct child (`child.wait()`), then calls `killpg(pgid, SIGKILL)`. `Drop` (which runs when `wait(mut self)` returns) calls it again.
- If the group became empty when the child was reaped, its id (= the child's pid) is free. The kernel may reuse it for a new process group leader, and our SIGKILL would then hit an unrelated group.
- The comment at line 510 ("not reused while any member of the group exists") is true, but it does not cover the moment after the last member has been reaped.

**Fix:**
- Kill the rest of the group before reaping the leader: wait with `waitid(P_PID, …, WEXITED | WNOWAIT)`, then `killpg`, then reap.
- Mark the tree as killed so `Drop` does not signal again after a reap.
- On Windows the Job handle has no such problem.

### M6 — The trusted FFmpeg publisher changed without an ADR or owner decision
**Where:** `tools/manifest.json:31-33`, `docs/adr/0007-video-consent.md` (D1), DESIGN_NOTES Round 11.

**What happens:**
- D1 and ADR-0007 name **`BtbN/FFmpeg-Builds`** as the "official source".
- The manifest downloads from `github.com/FFmpeg-Builds/FFmpeg-Builds/…`, and the consent text shows that as the source. The only justification is in DESIGN_NOTES ("the repository moved; the old URL 301-redirects").
- The account that publishes a binary we download and run is a trust decision (AGENTS §8), not an implementation detail. This review could not verify the move or the hashes offline.

**Fix:**

- Amend ADR-0007 D1 with the new name and the date it was checked.
- Re-check D16's FFmpeg hashes from that tag's `checksums.sha256`.

### M7 — The "IPC cannot grant consent" test misses the IPC server itself
**Where:** `crates/eid-media/tests/g2_tools.rs:322-348`.

**What happens:**
- `ipc_and_native_messaging_cannot_grant_consent` scans only `eid-ipc` and `eid-native-host`.
- The IPC server (`eid serve`) and the remote commands live in `eid-cli` (`serve.rs`, `remote.rs`), and `eid-cli` now depends on `eid-media`. Today neither file mentions video or consent (checked by grep in this review), but no test keeps it that way, so D7 is not enforced.

**Fix:**

- Keep the test name and add the positive control that the scan does find `consent` in `video.rs`.

- **m5 — A file can be lost silently between the archive and our publish.** `video.rs:805-810`: yt-dlp records an item in `.eid-archive.txt` when its download succeeds, before we publish. If the staging folder is emptied in between (antivirus, the user), the next run sees "archive lists it, staging empty" and marks it `Done` without a file. ## Checked and found sound
- The flag allowlist is structural (`args::check`): valued flags only as `--flag=value`, exactly one argument after `--`. `FORBIDDEN` covers the plan §3 list plus `--username`/`--password`/`-P`/`--paths`/`--print-to-file`/`--alias`/`--client-certificate`.
- No user or network text reaches a template or path option. Tool paths with `$`, `%`, control or bidi characters are refused.
- `MediaUrl`: http(s) only, no userinfo, no whitespace, control or bidi characters, no leading `-`.
- The child environment is an allowlist built with `env_clear`. `YTDLP_NO_PLUGINS=1`.
- Windows: `CREATE_NO_WINDOW | CREATE_SUSPENDED`, then a Job with `KILL_ON_JOB_CLOSE` (non-inheritable handle), then resume. Fails closed when resuming fails.
- No `cfg(windows)`, `Command` or `tokio::process` in `src` outside `eid-platform` (grep, and `platform_code_and_process_spawning_only_in_eid_platform` passed).
- Pipes are drained concurrently with `Head`/`Tail` caps. A truncated `-J` is refused before parsing. Lists and strings from `-J` are bounded.
- The manifest is compiled in: pinned GitHub release path, https, no port, query or userinfo, hosts can only be narrowed, `*.exe` only, safe entry names. The engine enforces the host allowlist on every redirect hop and a size cap.
- Zip: only the named entries; every entry is cut at its pinned size and checked against its own SHA-256; created files are removed on error.
- D11: hashes are read through a share-read-only handle with no reparse follow, and the handles are held until the tree has exited.
- Consent: text from the locale files plus the manifest's tool list, hashed as rendered; immediate refusal without a terminal; revoking clears the record before deleting the tools.
- The state file: private atomic write, checksummed, bounded, `deny_unknown_fields`, validated (ids, numbers, width, confined file names). It is refused, never repaired.
- The folder lock (`.eid-lock`).
- The secrets sentinel test has a positive control (the token does reach the fake).
- CI: `cargo deny` is blocking on Linux. On Windows, ffprobe is verified against the manifest hashes. The release artifact comes from a separate `cargo build --release -p eid-cli`, which does not unify the `test-hooks`/`test-faults` dev-dependency features.
- Clean room: nothing found that looks copied from IDM, Ant, Ezoo or Zajil. The fixtures are synthetic `lavfi` output, with the command and hashes documented.
