## Round 4 — P1 independent review fixes (docs/reviews/P1.md, Claude review of the fixes)
* **SHA-256 is computed at every finish even when `compute_sha256 = false`** (disagreement with the review note "don't compute unless required"): the finalization record (name + SHA-256, written and fsynced BEFORE the rename, B2) is the only thing that lets a crash after the rename be recognised by CONTENT instead of by file size; without a digest the recovery would again trust a name+size. It is a deliberate cost (one sequential read of the file, now on the blocking pool); the digest is only RETURNED in `Outcome` when requested. Revisit only with a cheaper content identity.
* **`Last-Modified` alone** is a strong validator only if the server's `Date` is >= LM + 1 s (RFC 9110 §8.8.2.2: the resource may change twice within one second). Otherwise (no `Date`, unparsable, `Date <= LM`) it is dropped at the probe: never stored, never sent in `If-Range`, and a server with no other validator gets ONE stream and a whole-file restart (B3). Tests: Date == LM (one stream; 4 live responses before the rule) and Date == LM + 1 s (segmented).
* **B1 (critical follow-up):** `state::remove_backup` returns `Result`, retries a locked `.bak` (8 attempts, growing delay) and does `sync_dir`; a restart that cannot delete the old `.bak` stops BEFORE truncating. A surviving `.bak` would let `load` fall back to an older generation next to new-generation data.
* **A→B→A needs no generation id in v1.** Argument: a restart is `save(new state, zero frontier)` → `remove_backup` (checked, durable) → truncate. After the second step no file on disk (primary or `.bak`) can certify bytes of an older generation, and before the truncation the data on disk is still the old generation, which the still-consistent state describes. So at every instant each state file on disk describes the data currently on disk, or a prefix of it that is still valid; the only way an older state could come back is a surviving `.bak`, which the checked removal closes. A server that returns to the first representation WITH THE SAME validator and length is, by the definition of a validator, indistinguishable from "unchanged": a locally stored generation id cannot detect it, because the id is client-local and the server shows nothing different. If the validator differs, the existing validator comparison already forces a restart. Revisit only if a server class with unstable validators matters (then weak-validator policy above applies).
* **M1:** per-job lock FILE `<name>.eid-lock` (not the part file: it must exist when the part is missing, and the part is deleted/recreated by restarts). Acquired before `state::load`; handed into the restart path; deleted only at the end of a finished job while still locked. The lock file is part of the job's file set (the orphan test allows it). After locking, the handle's identity (dev+ino / volume serial+file index) is compared with the path and an orphaned inode is retried (the file is deleted while locked, so a waiter could otherwise lock an orphan while a third process owns the new file); delete-pending/sharing violations on Windows become `Busy`. Windows `LockFileEx` and these Windows paths are NOT TESTED on real Windows.
* **`is_lock_contention` maps Windows `ERROR_ACCESS_DENIED` (5), `ERROR_SHARING_VIOLATION` (32) and `ERROR_LOCK_VIOLATION` (33) to `Busy`.** Access-denied is what a delete-pending lock file returns, so it must be Busy, but a REAL permission problem on the lock file would also be reported as `Busy` (the user sees "busy" instead of "access denied"). Accepted for v1 because the lock file is created by the same user in the download directory; revisit if such reports appear. Always `false` on Unix. NOT TESTED on real Windows.
* **M4:** each job runs on its own task; dropping/aborting the caller only cancels (drop guard). Residual: a process kill still relies on checkpoints; hooks `set_pause_point`/`set_panic_point` are `test-faults` only.
* **drop(resp):** probe 416 fallback and single-stream retry now drop the previous response/body before the next request. The kernel may still show the old socket briefly (hyper closes asynchronously) — see STATUS (#[ignore]d 416 test) and ADR-0012 (proposed).

## Round 5 — coordinator checkpoint task (PR5, Claude review of the Windows CI diagnosis)
* A slow `checkpoint()` (part-file `sync_data` + state fsync/`MoveFileEx`) used to run *inside* the `run_ranged` `select!`, next to `ramp.tick()` and worker reassignment. Default `interval` missed-tick behavior is Burst, so after a long checkpoint the coordinator could immediately run another and almost never ramp or split. That is the cause of `slow_segment_is_split` (and extra limiter wall-time) on 2-vCPU Windows runners; no ADR and no new dependencies (an internal change that keeps the durability order).
* **Now:** one background task per `run_ranged`. The coordinator only signals it (`Notify` + a coalescing flag) and never awaits the I/O. At most one checkpoint runs at a time; a request that arrives during a run is merged and the next run takes a *fresh* snapshot immediately before `sync_data` (snapshot → sync → save), then save. `MissedTickBehavior::Delay` is set on the checkpoint *and* ramp intervals so a stall cannot enqueue a burst of ticks.
* The task is **joined** (its `spawn_blocking` is joined, never aborted) before any later state write: the final checkpoint, finalize/`remove_all`, a ServerChanged restart, and cancel. Without the join, an in-flight old-generation checkpoint could finish after the restart wrote the new-generation state and overwrite it (B1 returning), or recreate a state file after `remove_all`. A checkpoint error is sent back to the coordinator over a channel. The M4 supervised job drains this join as well.
* Tests (barriers, no property timing bounds) in `g11_ckpt_task.rs`: (a) a parked checkpoint must still allow a `Split` and the ramp to reach the cap; (b) finish while parked ⇒ no leftover state, checkpoint events only after release; (c) parked during ServerChanged ⇒ new-generation state is not written before the join and is not overwritten after (B1); (d) cancel while parked, then resume, exact SHA. NOT TESTED on real Windows.

### متابعة مراجعة PR5 — طلب المالك الحالي
* البرومبت: إصلاح دوران قناة أخطاء checkpoint المغلقة، تأخير `Restarted` حتى حفظ حالة الجيل الجديد وحذف النسخة الاحتياطية، إضافة `Drop` إلى `CkptCtl`، وتسمية حالات اختبار `g11_ckpt_task`؛ دون تبعيات أو تعديل PLAN أو الحدود الزمنية أو commit/push.
* أُضيف `ckpt_closed` لحجب فرع القناة بعد إغلاقها. مسار checkpoint يحترم `fault::fail("before_sync")`؛ الحالة (e) توقف عاملاً عند `write_reserved` وتتحقق من خطأ الحفظ وعدد دورات التصريف المحدود، بعداد خاص بميزة `test-faults` (لا عمل في بناء الإنتاج).
* سبب إعادة البدء يبقى معلقاً في التحميل ومساري الاستكمال حتى نجاح حفظ الحالة الجديدة وحذف `.bak`؛ يصدر الحدث قبل `restart_truncated`. الحالة (c) تنتظر 300ms مع checkpoint القديم متوقفاً وتتحقق من غياب الحدث وبقاء A، ثم تتحقق من B فور الحدث وفي كل تحميل ناجح للحالة حتى النهاية وبصمة B النهائية. الحالة (f) تحقن فشل كتابة حالة إعادة البدء وتتحقق من عدم إصدار الحدث.
* `Drop` يطلب إيقاف مهمة checkpoint ويلفت `Notify`، ولا يُجهض `spawn_blocking` الجاري؛ المسار العادي يبقى ينضم إلى المهمة قبل أي كتابة لاحقة.
* الحالات (a–f) تعمل تسلسلياً في دالة اختبار واحدة لأن pause/fail hooks عامة للعملية. رسائل الحالات وغطاء التقاط panic حول كل حالة يذكران اسمها، بما يشمل فشل المساعدات المشتركة.
* التحقق المحلي: `cargo fmt` و`cargo clippy --workspace --all-targets -- -D warnings` نجحا. اختبار `cargo test -p eid-engine --test g11_ckpt_task`: صفر ناجح، اختبار واحد فشل قبل تنفيذ السيناريوهات لأن البيئة تمنع bind لخادم loopback (`Operation not permitted`). السلوك لم يُختبر هنا ولا على Windows الحقيقي.

## Round 6 — M2: the published file is the verified file (P1 batch 1)
* **What changed:** finalization publishes the *retained verified handle*, not "whatever the part name refers to". Linux: `linkat("/proc/self/fd/N", dest, AT_SYMLINK_FOLLOW)` (prevention; falls back only on ENOENT/EPERM/EACCES from /proc). Other Unix: identity check of the source name, `link`, identity check of the destination; on a mismatch our link is removed ONLY if `dest` and `part` are still two names of the same foreign inode (so no data is lost); anything else is left untouched. Windows: pre-check, `MoveFileExW` as before, post-check, non-destructive rollback only if the destination still names exactly the entry we moved (**detect, not prevent**). Final destination re-check before `Finished`.
* **Recovery hole:** a crash between link and unlink left part+dest as two names of one inode and `resume` failed forever on the nlink>1 refusal. Now exactly that pair (same inode AND two links AND size+SHA-256 equal to the finalization record, hashed through the held handle) is finished; everything else stays strictly refused.
* **Stale claim fixed (wording only):** the advisory job lock is on `<name>.eid-lock`, not on the data file (comments in `fs.rs`/`download.rs`, the `Busy` text, STATUS).
* **Residual risk (honest):** a same-user process with write access to the directory can still tamper with the destination after our final check and with sidecars/locks; check-then-unlink of the part name is two operations. We guarantee a substituted object is never published *as the verified download* on Linux, and is detected/refused elsewhere, with rollback limited to cases where no data can be lost — not that a shared directory is immutable. Pathname snapshots cannot prove ownership atomically: a stranger swapping `dest` in the instant between our identity check and our unlink/rename-back (a few microseconds) can still be affected by that single operation (Unix: unlink of one name; Windows: rename-back, never an overwrite). Fully closing it needs handle-bound operations (M2b).
* **M2b (deferred, owner decision after Windows CI evidence):** handle-bound rename on Windows via `SetFileInformationByHandle(FileRenameInfoEx)` (needs DELETE access on the part handle, adds sharing-conflict failure modes with AV/indexers, cannot be exercised on the Linux box).
* **Codex code review of the M2 diff (`reports/p1b1_codex_review_*.txt`):** 6 findings. Accepted and fixed: (2) recovery re-verifies that the hashed handle still names BOTH paths with exactly two links before dropping the part (tests `recovery_refuses_a_destination_substituted_while_hashing`, `…third_link…`); (3) recovery opens with `O_NONBLOCK|O_NOFOLLOW` on a blocking thread (`recovery_open_never_blocks_on_a_fifo`); (4) a two-link candidate that fails verification is refused with the part+state kept, also for non-resumable states (restart path no longer reachable; test loops resumable/non-resumable); (5) the seam tests for rollback now run on every platform and a Windows-only rollback-failure test was added; (6) the Linux-only assert became cfg-selected per platform. Partially accepted: (1) rollback now requires `dest` and `part` to still be one foreign inode (no data lost) and the docs no longer claim "never"; the residual microsecond race stays documented (M2b). Not done: a seam that swaps `dest` *before* the identity snapshot (it is indistinguishable from a link to a foreign inode by design).
* **Round 3 (last Codex finding, fixed):** the part-absent recovery branch (pre-existing) now re-checks, after hashing, that the destination name still refers to the hashed handle; a swap during hashing is refused with the state kept (`recovery_without_a_part_refuses_a_destination_substituted_while_hashing`, red-first).

## Round 7 — P1 closure fixes and P2 design (this session)
* **M3:** `Config::header_timeout` existed but nothing used it; `reqwest`'s `connect_timeout` ends with the TCP connect and the engine's stall timer only watches the body, so a server that never finished its headers blocked a job forever. Now every `send()` goes through `http::send_bounded` (probe retry loop, ranged workers, Grabber). The deadline spans the whole redirect chain by construction (`send()` follows redirects internally).
* **M5 (Unix):** the `.eid-part` file is created `0600`; it may hold authenticated bytes while the transfer runs. The FINAL file gets `0666 & !umask` on the verified handle (`set_default_data_permissions`, umask read from `/proc/self/status` because `umask(2)` can only be read by changing it, which races with other threads) before it is published. Rejected alternative: leave the final file private (surprising: other local users/services such as a media server could not read downloads). Windows privacy is still NOT enforced (inherits the folder ACL); the tests no longer treat "unknown" as proof and are `unix:` in `required_tests.txt`.
* **M6:** Windows Ctrl-C needs a real console; a hollow test that passes and leaks a child is worse than "NOT TESTED". The test is now `cfg(unix)` + MANUAL-TESTS #14. The symlink pre-check fails loudly everywhere.
* **M7 / virtual time (OPEN, needs the owner):** PLAN G3 says the 429 test must use `start_paused`. With real sockets this cannot work: tokio's auto-advance jumps to the next timer whenever the runtime is idle, including while it only waits for the socket, so every `stall_timeout`/`header_timeout` timer fires at once. What exists instead: (1) the Retry-After arithmetic is pure and tested without any clock; (2) the queue/scheduler logic, which owns most timing in P2, runs on the virtual clock with a fake runner; (3) the 429 integration test measures with the server's own timestamps. Making the engine's timeouts injectable (a clock trait) would allow it but is an engine change and therefore a decision for the owner.
* **M7 / determinism:** a seed fixes the schedule (sizes, cuts, stalls, injected disk error) and the jitter DECISION stream (splitmix64 over `(seed, call index)`); which OS thread consumes which decision is still up to the scheduler, so a failing seed is replayed in a loop (`EID_SEED`/`EID_REPEAT`), not assumed bit-reproducible. The injected disk error is `fault::fail("write_data")` placed after the reservation and before the write; it ends the job (a write error is fatal by design) and the test then resumes it to the exact bytes.
* **m1:** the collision suffix is budgeted BEFORE the stem is shortened; a "huge extension" (> 16 bytes) is treated as part of the stem.
* **m3:** HTTP-date `Retry-After` is read relative to the response's own `Date` (a skewed local clock must not matter; falls back to the local clock only when `Date` is absent). A past or malformed date returns `None` so the caller backs off normally instead of retrying immediately in a loop.
* **m2:** the set-up block of a download (initial state write + `.bak` removal + truncate + preallocate) is one blocking-pool task, and so are `state::load` and `preallocate` on resume. Not moved (still short metadata calls on the executor): `claim_files`, opening the part file, the job lock.
* **P1 open items (a)(b)(c) from PR7 were NOT touched** (PLAN: owner approval required). `store.rs` (new code) avoids (a) by construction: only successfully read and invalid content is quarantined, never on an I/O error.
* **P2 architecture:** queue DECISIONS are a pure function (`QueueSet::plan(now)`) so they are tested exhaustively without tasks or time; the driver (`scheduler.rs`) only executes the plan and records results. Time enters through `Clock` and tokio timers, real downloads through `JobRunner` (the engine in production, a fake in timing tests), power actions through `PowerControl` (mock now, platform in P3). `queues.json` holds NO credentials: `user:pass@` is stripped when an item is added and kept in memory only for that run (so after a restart an item that needed credentials fails with 401 until it is added again; accepted for v1 per REQUIREMENTS "no stored site credentials").
* **P2 import safety:** an imported list cannot name a directory at all (no field exists), names/sub-folders are re-sanitized to one component, `user:pass@` is dropped, the whole file is rejected when it breaks a size or count bound (a half-imported hostile file is worse than none), CSV cells that Excel would execute are prefixed with `'` on export and unprefixed on import.
* **P2 Grabber:** a hand-written HTML scanner instead of a new dependency (no `html5ever`/`scraper`; DEPENDENCIES.md unchanged). A tag longer than 4096 bytes is skipped as junk so hostile input costs O(n); raw-text elements are skipped by scanning for `</name` without copying the rest of the page. Known limit: it is not an HTML5 parser (unquoted attribute edge cases, `<a>` nesting rules), which is acceptable for a link lister but means odd pages can lose links.
