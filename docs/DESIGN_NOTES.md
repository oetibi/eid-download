## Round 4 — P1 independent review fixes (docs/reviews/P1.md, Claude review of the fixes)
* **SHA-256 is computed at every finish even when `compute_sha256 = false`** (disagreement with the review note "don't compute unless required"): the finalization record (name + SHA-256, written and fsynced BEFORE the rename, B2) is the only thing that lets a crash after the rename be recognised by CONTENT instead of by file size; without a digest the recovery would again trust a name+size. It is a deliberate cost (one sequential read of the file, now on the blocking pool); the digest is only RETURNED in `Outcome` when requested. Revisit only with a cheaper content identity.
* **`Last-Modified` alone** is a strong validator only if the server's `Date` is >= LM + 1 s (RFC 9110 §8.8.2.2: the resource may change twice within one second). Otherwise (no `Date`, unparsable, `Date <= LM`) it is dropped at the probe: never stored, never sent in `If-Range`, and a server with no other validator gets ONE stream and a whole-file restart (B3). Tests: Date == LM (one stream; 4 live responses before the rule) and Date == LM + 1 s (segmented).
* **B1 (critical follow-up):** `state::remove_backup` returns `Result`, retries a locked `.bak` (8 attempts, growing delay) and does `sync_dir`; a restart that cannot delete the old `.bak` stops BEFORE truncating. A surviving `.bak` would let `load` fall back to an older generation next to new-generation data.
* **A→B→A needs no generation id in v1.** Argument: a restart is `save(new state, zero frontier)` → `remove_backup` (checked, durable) → truncate. After the second step no file on disk (primary or `.bak`) can certify bytes of an older generation, and before the truncation the data on disk is still the old generation, which the still-consistent state describes. So at every instant each state file on disk describes the data currently on disk, or a prefix of it that is still valid; the only way an older state could come back is a surviving `.bak`, which the checked removal closes. A server that returns to the first representation WITH THE SAME validator and length is, by the definition of a validator, indistinguishable from "unchanged": a locally stored generation id cannot detect it, because the id is client-local and the server shows nothing different. If the validator differs, the existing validator comparison already forces a restart. Revisit only if a server class with unstable validators matters (then weak-validator policy above applies).
* **M1:** per-job lock FILE `<name>.eid-lock` (not the part file: it must exist when the part is missing, and the part is deleted/recreated by restarts). Acquired before `state::load`; handed into the restart path; deleted only at the end of a finished job while still locked. The lock file is part of the job's file set (the orphan test allows it). After locking, the handle's identity (dev+ino / volume serial+file index) is compared with the path and an orphaned inode is retried (the file is deleted while locked, so a waiter could otherwise lock an orphan while a third process owns the new file); delete-pending/sharing violations on Windows become `Busy`. Windows `LockFileEx` and these Windows paths are NOT TESTED on real Windows.
* **`is_lock_contention` maps Windows `ERROR_ACCESS_DENIED` (5), `ERROR_SHARING_VIOLATION` (32) and `ERROR_LOCK_VIOLATION` (33) to `Busy`.** Access-denied is what a delete-pending lock file returns, so it must be Busy, but a REAL permission problem on the lock file would also be reported as `Busy` (the user sees "busy" instead of "access denied"). Accepted for v1 because the lock file is created by the same user in the download directory; revisit if such reports appear. Always `false` on Unix. NOT TESTED on real Windows.
* **M4:** each job runs on its own task; dropping/aborting the caller only cancels (drop guard). Residual: a process kill still relies on checkpoints; hooks `set_pause_point`/`set_panic_point` are `test-faults` only.
* **drop(resp):** probe 416 fallback and single-stream retry now drop the previous response/body before the next request. The kernel may still show the old socket briefly (hyper closes asynchronously) — see STATUS (#[ignore]d 416 test) and ADR-0012 (proposed).

## Round 5 — coordinator checkpoint task (PR5, Claude review of the Windows CI diagnosis)
* A slow `checkpoint()` (part-file `sync_data` + state fsync/`MoveFileEx`) used to run *inside* the `run_ranged` `select!`, next to `ramp.tick()` and worker reassignment. Default `interval` missed-tick behavior is Burst, so after a long checkpoint the coordinator could immediately run another and almost never ramp or split. That is the cause of `slow_segment_is_split` (and extra limiter wall-time) on 2-vCPU Windows runners; no ADR and no new dependencies (an internal change that keeps the durability order).
* **Now:** one background task per `run_ranged`. The coordinator only signals it (`Notify` + a coalescing flag) and never awaits the I/O. At most one checkpoint runs at a time; a request that arrives during a run is merged and the next run takes a *fresh* snapshot immediately before `sync_data` (snapshot → sync → save), then save. `MissedTickBehavior::Delay` is set on the checkpoint *and* ramp intervals so a stall cannot enqueue a burst of ticks.
* The task is **joined** (its `spawn_blocking` is joined, never aborted) before any later state write: the final checkpoint, finalize/`remove_all`, a ServerChanged restart, and cancel. Without the join, an in-flight old-generation checkpoint could finish after the restart wrote the new-generation state and overwrite it (B1 returning), or recreate a state file after `remove_all`. A checkpoint error is sent back to the coordinator over a channel. The M4 supervised job drains this join as well.
* Tests (barriers, no property timing bounds) in `g11_ckpt_task.rs`: (a) a parked checkpoint must still allow a `Split` and the ramp to reach the cap; (b) finish while parked ⇒ no leftover state, checkpoint events only after release; (c) parked during ServerChanged ⇒ new-generation state is not written before the join and is not overwritten after (B1); (d) cancel while parked, then resume, exact SHA. NOT TESTED on real Windows.

### متابعة مراجعة PR5 — طلب المالك الحالي
* البرومبت: إصلاح دوران قناة أخطاء checkpoint المغلقة، تأخير `Restarted` حتى حفظ حالة الجيل الجديد وحذف النسخة الاحتياطية، إضافة `Drop` إلى `CkptCtl`، وتسمية حالات اختبار `g11_ckpt_task`؛ دون تبعيات أو تعديل PLAN أو الحدود الزمنية أو commit/push.
* أُضيف `ckpt_closed` لحجب فرع القناة بعد إغلاقها. مسار checkpoint يحترم `fault::fail("before_sync")`؛ الحالة (e) توقف عاملاً عند `write_reserved` وتتحقق من خطأ الحفظ وعدد دورات التصريف المحدود، بعداد خاص بميزة `test-faults` (لا عمل في بناء الإنتاج).
* سبب إعادة البدء يبقى معلقاً في التحميل ومساري الاستكمال حتى نجاح حفظ الحالة الجديدة وحذف `.bak`؛ يصدر الحدث قبل `restart_truncated`. الحالة (c) تنتظر 300ms مع checkpoint القديم متوقفاً وتتحقق من غياب الحدث وبقاء A، ثم تتحقق من B فور الحدث وفي كل تحميل ناجح للحالة حتى النهاية وبصمة B النهائية. الحالة (f) تحقن فشل كتابة حالة إعادة البدء وتتحقق من عدم إصدار الحدث.
* `Drop` يطلب إيقاف مهمة checkpoint ويلفت `Notify`، ولا يُجهض `spawn_blocking` الجاري؛ المسار العادي يبقى ينضم إلى المهمة قبل أي كتابة لاحقة.
* الحالات (a–f) تعمل تسلسلياً في دالة اختبار واحدة لأن pause/fail hooks عامة للعملية. رسائل الحالات وغطاء التقاط panic حول كل حالة يذكران اسمها، بما يشمل فشل المساعدات المشتركة.
* التحقق المحلي: `cargo fmt` و`cargo clippy --workspace --all-targets -- -D warnings` نجحا. اختبار `cargo test -p eid-engine --test g11_ckpt_task`: صفر ناجح، اختبار واحد فشل قبل تنفيذ السيناريوهات لأن البيئة تمنع bind لخادم loopback (`Operation not permitted`). السلوك لم يُختبر هنا ولا على Windows الحقيقي.

## Round 6 — M2: the published file is the verified file (P1 batch 1)
* **What changed:** finalization publishes the *retained verified handle*, not "whatever the part name refers to". Linux: `linkat("/proc/self/fd/N", dest, AT_SYMLINK_FOLLOW)` (prevention; falls back only on ENOENT/EPERM/EACCES from /proc). Other Unix: identity check of the source name, `link`, identity check of the destination; on a mismatch our link is removed ONLY if `dest` and `part` are still two names of the same foreign inode (so no data is lost); anything else is left untouched. Windows: pre-check, `MoveFileExW` as before, post-check, non-destructive rollback only if the destination still names exactly the entry we moved (**detect, not prevent**). Final destination re-check before `Finished`.
* **Recovery hole:** a crash between link and unlink left part+dest as two names of one inode and `resume` failed forever on the nlink>1 refusal. Now exactly that pair (same inode AND two links AND size+SHA-256 equal to the finalization record, hashed through the held handle) is finished; everything else stays strictly refused.
* **Stale claim fixed (wording only):** the advisory job lock is on `<name>.eid-lock`, not on the data file (comments in `fs.rs`/`download.rs`, the `Busy` text, STATUS).
* **Residual risk (honest):** a same-user process with write access to the directory can still tamper with the destination after our final check and with sidecars/locks; check-then-unlink of the part name is two operations. We guarantee a substituted object is never published *as the verified download* on Linux, and is detected/refused elsewhere, with rollback limited to cases where no data can be lost — not that a shared directory is immutable. Pathname snapshots cannot prove ownership atomically: a stranger swapping `dest` in the instant between our identity check and our unlink/rename-back (a few microseconds) can still be affected by that single operation (Unix: unlink of one name; Windows: rename-back, never an overwrite). Fully closing it needs handle-bound operations (M2b).
* **M2b (deferred, owner decision after Windows CI evidence):** handle-bound rename on Windows via `SetFileInformationByHandle(FileRenameInfoEx)` (needs DELETE access on the part handle, adds sharing-conflict failure modes with AV/indexers, cannot be exercised on the Linux box).
* **Codex code review of the M2 diff (`reports/p1b1_codex_review_*.txt`):** 6 findings. Accepted and fixed: (2) recovery re-verifies that the hashed handle still names BOTH paths with exactly two links before dropping the part (tests `recovery_refuses_a_destination_substituted_while_hashing`, `…third_link…`); (3) recovery opens with `O_NONBLOCK|O_NOFOLLOW` on a blocking thread (`recovery_open_never_blocks_on_a_fifo`); (4) a two-link candidate that fails verification is refused with the part+state kept, also for non-resumable states (restart path no longer reachable; test loops resumable/non-resumable); (5) the seam tests for rollback now run on every platform and a Windows-only rollback-failure test was added; (6) the Linux-only assert became cfg-selected per platform. Partially accepted: (1) rollback now requires `dest` and `part` to still be one foreign inode (no data lost) and the docs no longer claim "never"; the residual microsecond race stays documented (M2b). Not done: a seam that swaps `dest` *before* the identity snapshot (it is indistinguishable from a link to a foreign inode by design).
* **Round 3 (last Codex finding, fixed):** the part-absent recovery branch (pre-existing) now re-checks, after hashing, that the destination name still refers to the hashed handle; a swap during hashing is refused with the state kept (`recovery_without_a_part_refuses_a_destination_substituted_while_hashing`, red-first).

## Round 7 — P1 closure fixes and P2 design (this session)
* **M3:** `Config::header_timeout` existed but nothing used it; `reqwest`'s `connect_timeout` ends with the TCP connect and the engine's stall timer only watches the body, so a server that never finished its headers blocked a job forever. Now every `send()` goes through `http::send_bounded` (probe retry loop, ranged workers, Grabber). The deadline spans the whole redirect chain by construction (`send()` follows redirects internally).
* **M5 (Unix):** the `.eid-part` file is created `0600`; it may hold authenticated bytes while the transfer runs. The FINAL file gets `0666 & !umask` on the verified handle (`set_default_data_permissions`, umask read from `/proc/self/status` because `umask(2)` can only be read by changing it, which races with other threads) before it is published. Rejected alternative: leave the final file private (surprising: other local users/services such as a media server could not read downloads). Windows privacy is still NOT enforced (inherits the folder ACL); the tests no longer treat "unknown" as proof and are `unix:` in `required_tests.txt`.
* **M6:** Windows Ctrl-C needs a real console; a hollow test that passes and leaks a child is worse than "NOT TESTED". The test is now `cfg(unix)` + MANUAL-TESTS #14. The symlink pre-check fails loudly everywhere.
* **M7 / virtual time (OPEN, needs the owner):** PLAN G3 says the 429 test must use `start_paused`. With real sockets this cannot work: tokio's auto-advance jumps to the next timer whenever the runtime is idle, including while it only waits for the socket, so every `stall_timeout`/`header_timeout` timer fires at once. What exists instead: (1) the Retry-After arithmetic is pure and tested without any clock; (2) the queue/scheduler logic, which owns most timing in P2, runs on the virtual clock with a fake runner; (3) the 429 integration test measures with the server's own timestamps. Making the engine's timeouts injectable (a clock trait) would allow it but is an engine change and therefore a decision for the owner.
* **M7 / determinism:** a seed fixes the schedule (sizes, cuts, stalls, injected disk error) and the jitter DECISION stream (splitmix64 over `(seed, call index)`); which OS thread consumes which decision is still up to the scheduler, so a failing seed is replayed in a loop (`EID_SEED`/`EID_REPEAT`), not assumed bit-reproducible. The injected disk error is `fault::fail("write_data")` placed after the reservation and before the write; it ends the job (a write error is fatal by design) and the test then resumes it to the exact bytes.
* **m1:** the collision suffix is budgeted BEFORE the stem is shortened; a "huge extension" (> 16 bytes) is treated as part of the stem.
* **m3:** HTTP-date `Retry-After` is read relative to the response's own `Date` (a skewed local clock must not matter; falls back to the local clock only when `Date` is absent). A past or malformed date returns `None` so the caller backs off normally instead of retrying immediately in a loop.
* **m2:** the set-up block of a download (initial state write + `.bak` removal + truncate + preallocate) is one blocking-pool task, and so are `state::load` and `preallocate` on resume. Not moved (still short metadata calls on the executor): `claim_files`, opening the part file, the job lock.
* **P1 open items (a)(b)(c) from PR7 were NOT touched** (PLAN: owner approval required). `store.rs` (new code) avoids (a) by construction: only successfully read and invalid content is quarantined, never on an I/O error.
* **P2 architecture:** queue DECISIONS are a pure function (`QueueSet::plan(now)`) so they are tested exhaustively without tasks or time; the driver (`scheduler.rs`) only executes the plan and records results. Time enters through `Clock` and tokio timers, real downloads through `JobRunner` (the engine in production, a fake in timing tests), power actions through `PowerControl` (mock now, platform in P3). `queues.json` holds NO credentials: `user:pass@` is stripped when an item is added and kept in memory only for that run (so after a restart an item that needed credentials fails with 401 until it is added again; accepted for v1 per REQUIREMENTS "no stored site credentials").
* **P2 import safety:** an imported list cannot name a directory at all (no field exists), names/sub-folders are re-sanitized to one component, `user:pass@` is dropped, the whole file is rejected when it breaks a size or count bound (a half-imported hostile file is worse than none), CSV cells that Excel would execute are prefixed with `'` on export and unprefixed on import.
* **P2 Grabber:** a hand-written HTML scanner instead of a new dependency (no `html5ever`/`scraper`; DEPENDENCIES.md unchanged). A tag longer than 4096 bytes is skipped as junk so hostile input costs O(n); raw-text elements are skipped by scanning for `</name` without copying the rest of the page. Known limit: it is not an HTML5 parser (unquoted attribute edge cases, `<a>` nesting rules), which is acceptable for a link lister but means odd pages can lose links.


## Round 8 — P3 (IPC, Native Messaging) — decisions taken inside the approved ADR-0002/ARCHITECTURE
* **One framing for both channels** (`eid-ipc::frame`): 4-byte little-endian length + JSON, ≤ 1 MiB, length checked before any allocation/read. Native Messaging specifies *native* byte order; every target is little-endian and a `compile_error!` guards the assumption.
* **Strict messages:** `deny_unknown_fields` everywhere. The tests found that serde **ignores extra fields on unit variants of an internally tagged enum**, so `Ping`/`List`/`Shutdown` are struct variants (`{}`); `unknown_fields_wrong_version_and_bad_shapes_are_rejected` is the guard.
* **Idempotency** is a bounded in-memory map (id → command fingerprint + response) shared by all connections and checked under one lock, so racing duplicates run once (16-way race test). It does **not** survive an app restart: a retried id after a restart runs again. Accepted for v1 (the host retries within one session).
* **Least privilege for browsers:** only `ping` and `add` pass the native host. A caller never names a directory: the download folder is fixed by `eid serve`/the app; the caller may only suggest a sub-folder and a file name, both sanitized by the engine.
* **Single instance = endpoint ownership.** `first_pipe_instance(true)` (Windows) / "refuse to replace a live socket" (Unix). The IPC server claims the endpoint **before** rewriting the token file, so a second instance can never invalidate the first one's token.
* **Environment hooks (same trust as the user's own environment, not a new network surface):** `EID_IPC_ENDPOINT`, `EID_IPC_TOKEN_FILE`, `EID_NATIVE_HOST_APP` (program the host launches, always as `serve --endpoint .. --token-file ..`), `EID_NATIVE_HOST_READY_MS` (1..=60000). They exist so tests and portable installs can isolate themselves. **Rejected alternative:** none; if the owner dislikes them they can be compiled out behind a feature without changing the tests' intent.
* **Windows handle inheritance (real bug found by a test):** `std::process::Command` always sets `bInheritHandles=TRUE`, so a launched app inherits every inheritable handle of the native host, including the browser's stdout/stderr pipes — the browser would never see EOF. `spawn_detached` clears `HANDLE_FLAG_INHERIT` on the host's std handles for the duration of the spawn (guard must outlive the no-breakaway fallback attempt; it originally did not). **Known residual:** other inheritable handles a process holds are still inherited; the proper fix is `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`, which std cannot express (would need a raw `CreateProcessW`). Not done.
* **Not done in P3 (stated, not hidden):** DPAPI (`secret_protect`) — nothing consumes it yet; real system shutdown/sleep (`PowerControl` platform impl); explicit protected DACL for data/part/state files (MANUAL-TESTS #15); `register_native_host` is implemented in `eid-platform` but nothing calls it yet (installer hooks are P7); the host manifest's extension id is a parameter, no real extension exists (P6).

## Round 10 — P4 G1 (supervised spawn, eid-media core, fake yt-dlp): decisions inside the approved plan
* **Valued yt-dlp flags are always one argument `--flag=value`.** With a separate value argument, a value that starts with `-` could be read as a flag by some parsers; the joined form removes the question and makes the allowlist check purely structural (`args::check`: every argument before the single `--` is an allowed flag in its proper form, exactly one argument after it).
* **Two flags beyond the plan's "always" list, both in the allowlist:** `--encoding=utf-8` (yt-dlp's stdout encoding on Windows would otherwise follow the console code page and mangle Arabic titles in `-J`; `PYTHONUTF8`/`PYTHONIOENCODING` are excluded by the environment allowlist) and `--no-mtime` on downloads (we publish the file ourselves). Neither loads code, touches the network or a path.
* **No user format strings.** Quality is an enum (best / max height / mp3 / a `format_id` from the tool's own `-J`); a `format_id` must be 1–64 of `[A-Za-z0-9_.-]`, so it can never be a format-selection expression or a flag. Hostile ones in `-J` are dropped.
* **URLs for video may not carry `user:pass@`** (no sign-in in v1, and it keeps credentials out of the tool's command line and error text). Bidi/control characters and whitespace are refused; the accepted string reaches yt-dlp byte-exact.
* **Windows process tree:** `CREATE_SUSPENDED` + Job (`KILL_ON_JOB_CLOSE`) + Toolhelp32/`ResumeThread`, all inside `eid-platform` with `tokio::process` (std/tokio still build the command line; no hand-written `CreateProcessW`). The job is not breakaway-capable. When the direct child exits, the rest of its tree is killed (a leftover would keep our pipes open forever).
* **Red-check finding (real, fixed in the test):** `child_and_grandchild_have_no_console_window` first called `spawn` from the test process; there the test process has no console window, so the test **passed even without `CREATE_NO_WINDOW`**. Now the supervising process is started with `CREATE_NEW_CONSOLE` (it reports `"parent": true`, else the test fails as non-discriminating) and calls `spawn` from there; without the flag the test fails. Likewise `a_finished_child_takes_its_leftover_grandchildren_with_it` first let the grandchild sleep as long as the child (proved nothing); it now sleeps 600 s. A console window flashes briefly while these two Windows tests run on a desktop.
* **Known residual (unchanged from P3):** std/tokio create every child with `bInheritHandles=TRUE`, so yt-dlp inherits any *inheritable* handle eid holds (e.g. eid's own stdout pipe when a script captures eid). The job kill on exit bounds the lifetime; closing it fully needs `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` (raw `CreateProcessW`, rejected by the plan). Observed during a red check: with the job disabled, leftover sleepers held cargo's pipe for 600 s.
* **Linux:** no equivalent of "killing eid kills the tree" (a process group survives the death of its creator); documented, not tested (the test is `windows:`).
* **Fake yt-dlp configuration through the URL**, because the child environment is an allowlist and cannot carry test settings. The fake refuses to run without the mandatory flags and only knows the constant output template, so builder regressions fail loudly.
* **Fixture clips** were generated locally with the pinned BtbN FFmpeg (owner's permission 2026-11-15; archive verified against the tag's `checksums.sha256`, kept in the session scratchpad only, nothing installed). Command and hashes: `crates/eid-fake-ytdlp/fixtures/README.md`.

## Round 11 — P4 G2 (consent, settings, tool manager): decisions inside the approved plan
* **Engine change (small, opt-in):** `Config::allowed_hosts` (initial URL + every redirect hop, exact host match) and `Config::max_total_bytes` (refuse unknown or larger total at the probe). Both `None` by default, so P1–P3 behaviour is unchanged. The plan says tool downloads go "through the engine with `expected_sha256`" and D14 limits hosts; the engine had no per-hop host check, so without this a redirect could have left GitHub. Tested in `tests/g19_tool_policy.rs` (127.0.0.1 vs `localhost` as two hosts).
* **Manifest rules beyond "https + host":** the asset must be `github.com/<owner>/<repo>/releases/download/<tag>/<asset>` with a fixed tag (not `latest`/`nightly`/`master`), no query, port or userinfo; a manifest can only narrow the compiled-in host list; tool files are plain `*.exe` names (so `.bat`/`.cmd`/scripts can never be installed); archive entries are relative plain components; a direct file must be the whole asset. The manifest is compiled in (`include_str!`), so "update" = install what this build pins.
* **FFmpeg URL:** BtbN's repository moved to `FFmpeg-Builds/FFmpeg-Builds`; the old URL 301-redirects. The manifest uses the new URL directly (same assets and hashes), which also avoids depending on a redirect from a renamed repository name.
* **Install layout:** `<root>/set-<manifest id>-<random>/` + `current.json`; build in `.staging-<random>`, verify all four files through handles, rename into place, switch `current.json` with `replace_atomic`, then delete the old set (best effort: a running job may still hold it on Windows; the next install retries). Any failure removes the staging folder and leaves the previous set current.
* **Consent text = translation file + tool list from the manifest**, hashed as rendered; a record matches if it equals the hash of the Arabic or the English rendering. New tool versions therefore require a new consent. `ConsentText` is `#[non_exhaustive]` so only `consent_text` can produce one. Revoking clears the record first, then deletes the tools (video is off even if deletion fails).
* **Settings file:** `settings.json` in the config dir, written by the same `write_private_atomic` as the IPC token (Unix 0600, Windows protected user-only DACL). A damaged, oversized, unknown-field or link file keeps video off (error, never "assume no consent and overwrite"). Windows DACL read-back for this file is covered by the token test of the shared writer, not by a test on `settings.json` itself.
* **Locked hashing (D11):** `eid_platform::fs::open_tool_locked` = read + `FILE_SHARE_READ` only + no reparse follow + plain-file check; the hash is read from that handle; the handles live in `LockedTools`, which the caller (G3) keeps until the tree exits. Hashing ~385 MB of tools at each job start is the cost the owner accepted; it runs on the blocking pool (`lock_blocking`).
* **ETXTBSY (Linux):** a just-installed tool can be "busy" for a moment when another thread forked meanwhile; `spawn` retries up to 5 times (150 ms in all). This is a short blocking pause on the calling thread (like process creation itself), noted against AGENTS §6.7.
* **CI ffprobe (D3):** `ci-windows` reads the FFmpeg asset from `tools/manifest.json`, caches it by its SHA-256, verifies the asset hash and the extracted `ffprobe.exe` hash, and sets `EID_FFPROBE` + `EID_REQUIRE_FFPROBE=1`. The ffprobe test is `windows:` (the manifest pins Windows binaries only); on Linux it is reported NOT TESTED. The script was dry-run locally with PowerShell 5.1 against the verified archive; CI uses pwsh 7.
* **Not checkable here:** `cargo clippy --target x86_64-unknown-linux-gnu` for eid-media, because it now depends on the engine (reqwest → rustls → ring needs a Linux C compiler that this machine lacks). eid-platform and eid-fake-ytdlp are still checked for Linux locally; eid-media on Linux only in CI.

## Round 12 — P4 G3 (`eid video info|get|consent|revoke`): decisions inside the approved plan
* **Order of a run:** consent → tools installed → tools locked + hashed (kept until the tree exits) → `-J` → download with the staging folder as cwd → we publish → staging removed. Nothing is fetched or started before consent; the no-consent test asserts zero requests on the local server and no tools/settings folders.
* **Consent in the CLI (D2):** `--yes-i-agree` (the text is still printed to stderr), or an interactive `yes` on a terminal. Without a terminal and without the flag: exit code **3** at once (never reads stdin). `eid video consent [--lang ar|en]` shows the text and the status; `eid video revoke` withdraws consent and deletes the tools. CLI messages (hints included) are English, like every CLI message since P1; the consent text itself comes from the translation files.
* **Staging folder = `<output dir>/.eid-video-<16 hex of SHA-256(url, quality)>`**, so the same command finds and continues the same partial download (resume reuses it; the fake proves it continues from the `.part` length). It is created with `create_dir`; an existing one is reused only if it is a real folder containing only plain files and folders. A link, junction or file there, or a link inside it, is refused, never followed or "repaired" (tested with a directory symlink, a junction on Windows and a file symlink inside; the test fails if it cannot create them).
* **Publishing:** exactly one finished `*.mp4`/`*.mp3` must be in staging; it is opened without following links and published with `publish_verified` (the engine's verified-handle publish: never overwrites, ` (n)` on collision); the name is `sanitize_file_name(title + ext)` fitted to the path limit; an empty title becomes `video`. Up front the output folder must leave room for the staging folder plus 96 units for yt-dlp's own temporary names, else a clear "too long" error before the tool runs.
* **Failure cleanup (bug found by the DRM test):** a `-J` failure left the fresh staging folder behind; now an empty staging folder is removed on any failure, a non-empty one (partial data) is kept for resume.
* **Cancellation:** Ctrl-C cancels a token; the download future is dropped, which kills yt-dlp's whole tree (G1). Exit 130 and a "run the same command again" message. Tested with SIGINT on Unix; on Windows with a hard kill of `eid` (the job dies with it) because a real console Ctrl-C needs a real console (MANUAL-TESTS #14).
* **Test hooks are a cargo feature (`test-hooks`) of eid-cli**, enabled only by its own dev-dependency (like `test-faults`): `EID_TEST_MANIFEST` (manifest file) and `EID_TEST_TOOLS_BASE` (local server, must be `http://127.0.0.1:...`). Evidence that a release build has none: `target/release/eid.exe` contains neither variable name (0 matches); the test build does.
* **Fake yt-dlp extended** (test only): call log via the URL's `log=` parameter (pid, argv, cwd, resume offset), `.part` + resume like yt-dlp, and a stall-while-a-flag-file-exists mode for the cancel test.
* **(ج) tests written, not run:** `tests/g3_real.rs` (real CC video "Big Buck Bunny" by the Blender Foundation, CC BY 3.0, + ffprobe; `%`/`$` in the working folder; planted plugins next to the exe and in the cwd; start-up time for D9). They download ~230 MB of tools; they wait for the owner's permission.

## Round 13 — P4 G4 (`eid video playlist`): decisions inside the approved plan
* **Order of a playlist run:** consent → tools installed and locked → `--flat-playlist -J` of the playlist → playlist folder (`<out>/<sanitized title>`, a link or file there is refused) → folder lock (`.eid-lock`, an OS lock that belongs to the process, so a killed run frees it) → state load (a bad state stops the run, nothing is renumbered or "repaired") → plan (D8) → state saved before the first download so numbers are fixed → items one by one → state saved after every item.
* **Numbering lives in `eid_media::playlist`** (pure logic + state file). A name is `<digits> - <title>.<ext>`; the title is sanitized **on its own first**, then the digits are put in front. (Sanitizing the whole string let `../../x` cut the number off; found by the numbering test, now also a unit test.) A device name such as `CON` becomes `_CON` and is still unique through its number.
* **State file** (`.eid-playlist.json`): `{schema, state{playlist_id, width, items[{id, number, status, file}]}, sha256}`, written with `write_private_atomic`, read with `open_regular_nofollow_read` and an 8 MiB bound, `deny_unknown_fields`, checksum over the state, then `validate()` (ids, numbers, width 2..=7, `file` only on done items, every `file` must be an already-sanitized single component and not start with `.`, no duplicate file names case-insensitively). Tested with 30 hostile variants plus a symlinked state file; each leaves the file and the folder byte-identical and the tool unstarted.
* **Archive:** `ARCHIVE_FILE = "../.eid-archive.txt"` — the per-item staging folders are created directly inside the playlist folder, so the relative path from the tool's working directory is the archive inside the playlist folder (D13). The constant carries no user or network text. A finished item whose state was lost is recognised through the archive (yt-dlp skips it, we mark it done without a file name).
* **Deselection is per run** (`--skip`), not stored: a skipped item stays `pending` with its number and is downloaded when a later run does not skip it.
* **Temporary vs permanent failures:** private/removed/sign-in/geo/DRM (by availability or by the tool's classified error) = `unavailable`, skipped for good, number kept, the run still succeeds; anything else (429, network) = failed, exit code 1, retried next run.
* **Fake yt-dlp extended** (test only): playlists from a JSON file (`list=`), per-item `error` kinds, `--download-archive`, `stall_id=`; each call-log line is one write.
* **Not decided here (for the review):** a playlist whose sanitized name equals another playlist's folder is refused rather than getting a suffix; `--skip` is by number only.

## Round 14 — P4 review M2 (retries and error classification): owner decisions 2026-11-16
* **Problem (docs/reviews/P4.md M2):** `hints::classify` searched the whole stderr, warnings included, and in a playlist `Unavailable/SignInRequired/Drm/Geo` made an item `unavailable` for good (never retried, exit 0). YouTube also answers "Video unavailable. This content isn't available" while it limits requests, so a whole playlist could be lost silently.
* **Classification:** only `ERROR:` lines decide, the last one first; a warning can only add the informational `MissingJsRuntime`. `Hint::Unavailable` (generic) is now split from the explicit `Private` and `Removed`; "try again later" counts as a rate limit. The generic needles "use --cookies" and "--username" are dropped (yt-dlp appends that advice to many errors).
* **What stops automatic retries (`Hint::blocks_auto_retry`):** DRM, private, removed (uploader / terminated account), sign-in / age / membership / premium, country restriction; and, as before, `private`/`needs_auth`/`subscriber_only`/`premium_only` in the listing (the non-yt-dlp value `unavailable` is no longer accepted there). Such an item is `unavailable`, keeps its number, the run still succeeds. Nothing is ever worked around.
* **Everything else is temporary:** an attempt counter in the state; after `MAX_ATTEMPTS` = 3 failed runs in a row the item is `failed`, not retried automatically, listed at every run, exit code 1.
* **`eid video playlist … --retry-failed <numbers|all>`:** resets only the named items that are `failed` or `unavailable` (status `pending`, attempts 0); other numbers are reported and left as they are. An item still restricted in the listing is marked again without asking the tool; DRM is refused again. Not combinable with `--list`.
* **State file schema 2:** `attempts` per item (`MAX_ATTEMPTS` exactly when `failed`, less otherwise). Schema 1 is still read (its own strict shape and checksum) and written back as schema 2 at the next saving run; ids, numbers, width, files and `done` are kept; a schema-1 `unavailable` came from the old classifier and becomes `pending` (an explicit restriction marks it again). `--list` writes nothing. Tested with a schema-1 file written by the pre-M2 code (`crates/eid-media/tests/fixtures/playlist-state-v1.json`).
* **Test changed with the owner's approval (Q5):** `private_or_deleted_item_is_skipped_and_keeps_its_number` keeps its name and meaning; it now also checks the manual retry (a removed video that came back is downloaded, a still-private listing item is not even asked, DRM is refused again).

## Round 15 — P4 review M4 (single-file formats remuxed to MP4): owner approval 2026-11-16
* **Problem (docs/reviews/P4.md M4):** the format strings fall back to `/b`; a single file keeps its container (`--merge-output-format` only applies to a merge), `finished_file(…, "mp4")` refused it after a complete download, and every rerun repeated the error.
* **Fix:** `--remux-video=mp4` for every video quality (allowlist + ADR-0003 amendment); yt-dlp remuxes with FFmpeg, no re-encoding, skips it for an MP4, fails and keeps the source when MP4 cannot hold the codecs. Audio (mp3) is unchanged.
* **Checked before publishing, without another tool:** `eid_media::container::check_mp4` walks the ISO-BMFF top-level boxes (first `ftyp`, a `moov`, boxes cover the file exactly; size 0 only as the last box; at most 100 000 boxes). It runs in `finished_file` (so a playlist counts a bad result as a failed attempt and goes on) and again through the handle that `publish` links into place. Running ffprobe ourselves was rejected: ADR-0003 says we launch only yt-dlp. It proves the container is whole, not the codecs.
* **Failure, cancel, resume:** a failed or cancelled remux publishes nothing and keeps the downloaded source in the staging folder; the same command later remuxes it without downloading again (tested with the fake, which mirrors yt-dlp: `.temp.mp4`, then rename, source removed; archive written only after post-processing).
* **Known limit:** a tool that reports success but leaves a bad MP4 and records the item in the download archive leaves that item failing until its staging folder is removed by hand (the bad file is never published or deleted by us). Real yt-dlp exits non-zero when FFmpeg fails; not tested with the real tool.
* **Rejected inside M4:** excluding `.temp.`/`.part` names in `finished_file`. It was untested and not needed for safety: a leftover partial conversion is either a second candidate (refused) or fails the container check.

## Round 16 — P4 review M3 (lost `.eid-playlist.json`): owner decisions 2026-11-16
(Round 15 was already taken by M4 on `main`, so M3 is recorded here.)
* **Problem (docs/reviews/P4.md M3):** with no state file, `plan(None, …)` numbered items by their current position and picked the width again, next to `NN - …` files and a non-empty `.eid-archive.txt`. An item added on top got `01` beside the old `01 - …`; a playlist grown past 99 switched width. Against D8 rules 1, 2, 6 and F11a(3).

* **Nothing is deleted, renamed or replaced.** `playlist::leftovers` only looks: `symlink_metadata` (no link is followed), the archive is read through `open_regular_nofollow_read` and only its first 64 KiB (blank = empty; larger than that = listing something), and the folder is listed once. Example names come from the disk, so the message replaces control characters and the invisible format characters (bidi marks and controls, zero-width, U+2028/2029, U+061C, BOM, soft hyphen) with `?` before `printable` runs.

* **`--list` is still allowed** (it writes nothing): the listing is shown after a `warning:` with the same text, plus that the numbers shown are positions in the current listing, not the numbers of the files already there.
* **Not refused:** a folder with no archive (or a blank one) and no numbered visible file, e.g. a first run into an existing folder with the user's own unnumbered files. Dot files (our lock, staging folders) are not "numbered files"; a leftover staging folder alone publishes nothing that a number could collide with.

(2) A user who renamed every published file and emptied the archive is not detected; numbering then starts again, as before. (3) The lock file `.eid-lock` is opened (created if missing) before the check, as for every run; it holds no state. (4) The folder lock only excludes other eid runs: another program that writes the archive or a numbered file between the check and the first `save` is not seen (accepted). The message therefore asks for a backup made after the last run there. A stricter rule (also refuse when a loaded state does not know a numbered file in the folder) would change runs that have a state, so it was not added inside M3. (6) `printable` itself (shared by other commands) still lets through the format characters listed above; only the names in this message get the stricter treatment here.
* **Test changed with the owner's approval:** only the tail of `playlist_sync_downloads_only_new_items_via_the_archive` (it expected the lost-state run to succeed and write a new state); it now expects the refusal, no download, the same five files, the same archive, and no new state. The part before it is unchanged.
* **Tests (red first: the three end-to-end ones fail with the CLI change removed):** `playlist_lost_state_with_archive_and_numbered_files_is_refused` (MP4 and MP3 numbered files and a non-empty archive; an item added on top; refused for a plain run, an audio run, `--retry-failed all` and `--skip 1`, each checked for no download, no state, no staging folder and the same names and SHA-256 of every entry; `--list` warns and writes nothing; a damaged state file is still the load error, not "missing"; numbered files alone also refuse; a new `-d` folder works and leaves the old one as it was), `playlist_lost_state_message_neutralises_names_and_list_survives_an_odd_archive` (a hard-linked archive and a numbered file whose name holds bidi, zero-width, separator and C1 characters: refused, none of them printed, `--list` still works, nothing changed; fails loudly without a hard link), `playlist_lost_state_restored_from_backup_continues_with_the_old_numbers` (a backup made after the last run), `playlist_without_state_in_a_folder_without_earlier_runs_starts_normally`, and in `eid-media`: `playlist_lost_state_leftovers_are_found_read_only`, `playlist_lost_state_archive_that_is_a_link_or_folder_counts_and_is_not_followed` (fails loudly if the symlink cannot be made), `numbered_names_are_recognised_by_shape_only`, `archive_name_is_the_file_the_tool_is_told_to_use`.
