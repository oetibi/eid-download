# ADR-0002: Named Pipe خاص بالمستخدم، لا منفذ localhost
**الحالة:** مقبول.
**السياق:** الإضافة ← البرنامج، وCLI ← البرنامج. منفذ HTTP محلي (كما يفعل Ezoo على 9614 حسب README) يعرّض لـ DNS rebinding وتعارض المنافذ وأي صفحة ويب تحاول الاتصال.
**الخيارات:** localhost HTTP موقّع · Named Pipe + Native Messaging · COM.
**القرار:** Native Messaging من المتصفح إلى `eid-native-host` (يتحقق المتصفح من معرّف الإضافة)، ثم Named Pipe `\\.\pipe\EidDownload-<SID>` بـDACL يقتصر على المستخدم الحالي ورفض العملاء البعيدين، مع مصافحة بتوكن عشوائي 256-بت في ملف خاص بالمستخدم. التوكن دفاع إضافي ولا يحمي من برنامج خبيث يعمل بنفس المستخدم (موثّق). على Linux: Unix socket بصلاحية 0600 للاختبارات.
**العواقب:** لا HTTP أبداً. DACL فاضي يرفض الجميع وNULL DACL يسمح للجميع — يجب الاختبار بحساب آخر على Windows.
**الدليل:** اختبار تكامل لرسائل مشوهة/كبيرة (P3)؛ فحص آلي في CI يمنع أي `TcpListener::bind` في crates الاتصال؛ **لم يُختبر ACL حقيقي على Windows** حتى P8.

**ملحق (مراجعة P3، 2026-11-15) — تحصين دون تغيير القرار:** أسماء الأنابيب عامة ويمكن تخمينها، فيستطيع مستخدم آخر إنشاء الأنبوب قبل التطبيق (انتحال). لذلك **يتحقق العميل قبل إرسال أي شيء** من أن العملية التي تخدم الأنبوب تعمل بالمستخدم نفسه (`GetNamedPipeServerProcessId` ثم SID صاحب التوكن؛ على Unix `peer_cred`)، ويفشل مغلقاً. أثر جانبي معروف: عميل غير مرتفع لا يستطيع فحص عملية مرتفعة فيُرفض الاتصال (MANUAL-TESTS #18). فتح الأنبوب يستعمل `SECURITY_IDENTIFICATION` افتراضياً في tokio فلا يستطيع الخادم انتحال هوية العميل. الاختبار الآلي يحاكي «خادم لمستخدم آخر» بتمرير SID متوقع مختلف؛ **اختبار حساب ثانٍ حقيقي = MANUAL-TESTS #17 (لم يُختبر)**. ملف التوكن على Windows يُنشأ بـDACL محمي لمستخدم واحد (يُقرأ راجعاً في الاختبار).
